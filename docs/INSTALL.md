# Building the port and getting it onto the console

*(Español: [INSTALL.es.md](INSTALL.es.md))*

Nine steps. Steps 1 to 3 are one-offs; from step 4 on, a rebuild is two commands.

Everything here was done on an **Xbox Series X** in Developer Mode. A Series S has never been tried —
see the README. The PC side is the same either way.

## 0. Before you start: where the commands go

This guide is full of blocks like this one. **They are all commands you type yourself** into a terminal
window, and each one says above it where from. If you have never used one, this section is everything you
need; if you have, skip it.

### The terminal: PowerShell

Everything in this guide goes into **PowerShell**, the ordinary Windows terminal:

1. Press the **Windows** key.
2. Type `powershell`.
3. Press **Enter** on *Windows PowerShell*.

A window opens with a line ending in `>`. That is where you type the command and press **Enter**.

**Moving to a folder.** Almost every command is typed *from a particular folder*, usually this
repository's. You get there with `cd` and the path, in quotes if it has spaces:

```powershell
cd "C:\Users\your-name\Downloads\bloody-roar-2-xbox"
```

**A shortcut that saves mistakes:** open the folder in File Explorer, click the address bar, type
`powershell` over whatever is there and press **Enter**. PowerShell opens already in that folder.

⚠ Some commands are long and are split across lines with a **backtick** (`` ` ``) at the end of each.
Copy them whole, backticks included: they are what says "continues on the next line".

### You do not need administrator — and it is better not to

Nothing in this guide needs "run as administrator". All of it was built and tested from an ordinary
account.

> ⚠ And in one step, being administrator actively **breaks** it: the certificate in §3 is created in the
> store of whichever user runs the command. Create it elevated and it lands in the administrator's store,
> so when you package — as yourself — `signtool` cannot find it and fails without saying why.
>
> The only thing that asks for administrator rights is the Visual Studio **installer**, and it asks on
> its own.

### How to tell whether a command worked

The ones here finish by saying what they did, and say so when something goes wrong too. A command that
prints nothing has usually worked; to be sure, this answers `True` when the previous one succeeded:

```powershell
$?
```

## 1. What you need first

| | |
|---|---|
| **The game project, already working on your PC** | [novapowers0/BloodyRoar2Recomp](https://github.com/novapowers0/BloodyRoar2Recomp), cloned with `--recurse-submodules`. Build it and play it on Windows first. If it does not run there, it will not run on a console, and you will be debugging two things at once |
| **Your own disc** | An NTSC-U dump of `SCUS-94424` (`.cue` + `.bin`, about 527 MiB) |
| **No retail BIOS** | Unlike some other psxrecomp titles, this one boots on the **OpenBIOS** the project ships, which is free software and is what goes inside the package. If you prefer your own retail BIOS, §9 says where it goes |
| **Visual Studio** | "Desktop development with C++", plus the Windows 10/11 SDK and Ninja. The version is not pinned: `configurar-uwp.ps1` finds it with `vswhere -latest`. What it actually needs is three things — `vcvarsall.bat` accepting the **`uwp`** argument, the **App Container CRT** at `VC\Tools\MSVC\<version>\lib\x64\store\`, and **`cl.exe /ZW`** compiling, because the WinRT entry point is C++/CX |
| **An SDL2 built for WindowsStore** | Step 2 |
| **An Xbox in Developer Mode** | Registered, with Device Portal reachable from your PC |
| **PowerShell** | The one Windows ships with (Windows PowerShell 5.1) is enough: **you do not need PowerShell 7** |

This port was developed against commit `eed1e8d1` of the game project, with the `psxrecomp` submodule at
`219a3627` and `recomp-ui` at `b688ca79` — the pins the project itself records in `framework_pins.txt`.
A much newer framework may have moved the code the patches anchor on; **every patch checks its anchor
and stops rather than mangling anything**, so you will know immediately and by name.

> ⚠ **Newer Visual Studio is not automatically better here.** Microsoft has been winding down UWP for
> years, and this port leans on two things already deprecated elsewhere: the `uwp` target of `vcvarsall`
> and the C++/CX extensions. If some release drops either, this recipe will not work on it however new
> it is.

### The recompiled C comes from your disc, and it comes first

The 56 files and 68 MB of C that *are* this game are generated by the project's own recompiler, from
your disc, on your machine. That happens in the normal PC flow of the game project, which is why step 1
asks for it working there first — and it has to be done **before** you build for the console, because
the recompiler is a desktop program and does not run inside the UWP toolchain.

If your project tree has a `generated/` folder with the `SCUS_944.24` C files in it, you are ready.

## 2. An SDL2 for WindowsStore

**SDL3 has no WinRT backend**, so the port uses the SDL2 backend. You need SDL2 built for
`WindowsStore` — 2.30.2 is what this was tested with.

> **Where to type this:** in **PowerShell** — press the **Windows** key, type `powershell` and press
> **Enter** — in an **ordinary** window: you do not need "run as administrator", from wherever you
> unpacked the SDL2 sources.

```powershell
cmake -S <sdl2-source> -B <sdl2-build> -G Ninja `
      -DCMAKE_SYSTEM_NAME=WindowsStore -DCMAKE_SYSTEM_VERSION=10.0 `
      -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=<sdl2-install>
cmake --build <sdl2-build> --target install
```

What you pass to `-Sdl2` later is the folder holding `SDL2Config.cmake`, usually
`<sdl2-install>/cmake` or `<sdl2-install>/lib/cmake/SDL2`.

---

## 3. A certificate to sign with

Developer Mode accepts self-signed packages. Create one, and **remember its subject** — the `Publisher`
in the manifest has to match it character for character.

⚠ This is where not opening the window "as administrator" really matters: the certificate is created in
the store of whichever user runs the command, so an elevated one would put it in the administrator's
store, and `signtool`, running as you, would not find it.

> **Where to type this:** in **PowerShell** — press the **Windows** key, type `powershell` and press
> **Enter** — in an **ordinary** window: you do not need "run as administrator", from any folder.

```powershell
$c = New-SelfSignedCertificate -Type Custom -Subject "CN=YourName" `
       -KeyUsage DigitalSignature -FriendlyName "UWP signing" `
       -CertStoreLocation "Cert:\CurrentUser\My" `
       -TextExtension @("2.5.29.37={text}1.3.6.1.5.5.7.3.3", "2.5.29.19={text}")
$c.Thumbprint     # this is what you pass as -Certificado
```

Then open `package/Package.appxmanifest` and replace the two `CHANGE-ME`:

```xml
<Identity Name="BloodyRoar2-Recomp" Publisher="CN=YourName" ProcessorArchitecture="x64" Version="1.0.0.0" />
...
<PublisherDisplayName>YourName</PublisherDisplayName>
```

The packer compares the two before it does anything and stops if they differ, which saves you finding
out at the `signtool` step.

## 4. Apply the UWP profile

This repository's folder is the one with `tools\` and `docs\` inside it:

> **Where to type this:** in **PowerShell** — press the **Windows** key, type `powershell` and press
> **Enter** — in an **ordinary** window: you do not need "run as administrator", from this repository's
> folder.

```powershell
python tools\apply_uwp.py <path-to-game-project-root>
python tools\apply_uwp.py --list      # the thirteen steps, in order, and what each one is for
```

It copies the WinRT entry point into `<project>\UWP\` and runs the thirteen patches in order; the fifth
of them is what registers that entry point in the game's own `CMakeLists.txt`. Every step is idempotent
and checks what it expects to find, so running it twice changes nothing, and if a step does not
recognise the tree it stops there instead of leaving it half done.

What it changes, and why each one: [`HOW-IT-WORKS.md`](HOW-IT-WORKS.md).

## 5. Configure and build

> **Where to type this:** in **PowerShell** — press the **Windows** key, type `powershell` and press
> **Enter** — in an **ordinary** window: you do not need "run as administrator", from this repository's
> folder.

```powershell
powershell -ExecutionPolicy Bypass -File tools\configurar-uwp.ps1 `
     -Raiz <project> -Build <build> -Sdl2 <sdl2 cmake dir> -Compilar
```

It enters the UWP toolchain (`vcvarsall x64 uwp`, found through `vswhere`) and configures with
**Ninja**. Not the Visual Studio generator: it is multi-config, and this framework writes one version
file per configuration, which CMake rejects with *"Evaluation file to be written multiple times"*.

`vcvarsall x64 uwp` matters by itself: it puts the App Container CRT on `LIB`, so the executable imports
`msvcp140_app.dll` instead of the desktop `msvcp140.dll`. With `vcvars64` the package installs and the
console refuses to launch it.

**The target is `psx-runtime-us`**, the USA region's. This project has one target per region — Europe,
USA, Japan and a universal one — and a package carries the executable of a single one; the universal
target would need the C of the other regions too, and that only comes out of their discs. If your dump
is another region, pass `-Objetivo psx-runtime-<region>` and change the target and `OUTPUT_NAME` in
`tools\parche_uwp_cmake_juego.py` to match.

Out comes `BloodyRoar2_Recompiled_USA.exe` in the build folder.

## 7. Package and sign

> **Where to type this:** in **PowerShell** — press the **Windows** key, type `powershell` and press
> **Enter** — in an **ordinary** window: you do not need "run as administrator", from this repository's
> folder.

```powershell
powershell -ExecutionPolicy Bypass -File tools\empaquetar-uwp.ps1 `
     -Build <build> -Salida <out> -Certificado <thumbprint> -Version 1.0.0.0
```

It assembles the executable, the manifest, your tiles, the initial configuration
(`config\settings.toml` of this repository, plus the `game_us.toml` and `game_options.toml` the build
produced), the bundled mod catalogue and the free OpenBIOS; rebuilds `resources.pri` with `makepri`
(without the default `<packaging>` block, which splits the PRI by scale and makes the console reject
it); packs with `makeappx`; and signs with your certificate.

It also writes `mods\state.toml` with **widescreen switched on**, because on a console there is no Mods
tab to tick it in. `-SinPanoramico` leaves it off. Point `-VCLibs` at `Microsoft.VCLibs.x64.14.00.appx`
to have it copied next to the output for installing, and `-Ajustes` at another `settings.toml` if you
want different defaults.

Out comes `<identity>_<version>_x64.msix`, about 8.9 MB. **The disc is not in it** — it goes to the
console separately, in step 9.

> ⚠ **Raise `-Version` on every single install.** Installing the *same* version on top of itself
> **unregisters** the package: the portal answers "operation completed successfully" and then the package
> vanishes from the list, stops resolving by name, and the app cannot be launched. And a "Success" from
> the portal does not prove it registered — check the list afterwards.

## 8. Install it on the console

### 8.1 The dependency: VCLibs

The executable imports the App Container CRT — `msvcp140_app.dll`, `vcruntime140_app.dll`,
`vccorlib140_app.dll` — which does not live in the package but in a **framework package** that has to be
installed on the console once. The manifest declares it:

```xml
<PackageDependency Name="Microsoft.VCLibs.140.00" MinVersion="14.0.33519.0"
                   Publisher="CN=Microsoft Corporation, O=Microsoft Corporation, L=Redmond, S=Washington, C=US" />
```

**The file you need is `Microsoft.VCLibs.x64.14.00.appx`** (~900 KB). You already have it: the Windows
SDK and Visual Studio install it here —

```text
C:\Program Files (x86)\Microsoft SDKs\Windows Kits\10\ExtensionSDKs\Microsoft.VCLibs\14.0\Appx\Retail\x64\Microsoft.VCLibs.x64.14.00.appx
```

⚠ **Two files are easy to grab by mistake and neither works:**

- `Microsoft.VCLibs.x64.14.00.Desktop.appx`, the one `aka.ms` links to, is the **Desktop Bridge** build.
  Different package, and the console will keep saying the dependency is missing.
- `…\Appx\**Debug**\x64\Microsoft.VCLibs.x64.Debug.14.00.appx` is only for packages signed in Debug
  configuration. This port builds Release.

It is installed **once per console**: later packages, and later versions of this one, already find it.

### Before you touch anything: how the console has to be

- **In Developer Mode**, with Dev Home installed. If it is not, that is a separate process with
  Microsoft and this guide does not cover it.
- **Powered on and with your profile signed in.** ⚠ With no user signed in the console **will not open
  applications**: the package installs, shows up in the list, and launching it does nothing. This is one
  of the costliest things to work out on your own.
- **On the same network as your PC.**
- **Its address**, which **Dev Home** shows you on the console itself. The Device Portal listens on port
  **11443** over HTTPS.
- **Portal username and password**: the ones you set in **Dev Home → Remote Access Settings** when you
  turned remote access on.

### 8.2 Upload it

Open `https://<console-ip>:11443` in the browser on your PC.

⚠ The browser will warn that **the site's certificate is not trusted**. That is normal and not a problem:
the certificate belongs to the console, which issues it itself. Go in anyway — in Edge and Chrome,
**Advanced** → **Continue to … (unsafe)**; in Firefox, **Advanced** → **Accept the Risk and Continue**.
It will then ask for the portal's username and password.

Once in, **My games & apps → Add**:

1. **App package** → your `.msix`.
2. **Certificate** → not needed: the package is signed and Developer Mode accepts it.
3. **Optional packages / Dependency** → add `Microsoft.VCLibs.x64.14.00.appx` here, the first time.
4. **Next → Install**, and wait for *Package successfully registered*.

Then **launch it once** and let it close or close it yourself: that first run is what creates the app's
data folder, which is where the disc goes in step 9.

### 8.3 If it says `There is not enough space on the disk`

This is not your console being full, and the message is misleading. **The first install of a package
family goes to `D:\DevelopmentFiles`**, a partition of about 5 GB that Developer Mode keeps for exactly
that; later *updates* of an already-registered family go somewhere else. That partition fills up with the
first version of everything you have ever sideloaded, and **uninstalling a game does not empty it** —
the folders stay behind.

So the fix is to make your package an **update** instead of a first install, with a *seed*:

> A **seed** is a package with the **same identity** as the real one — same `Identity Name` and same
> `Publisher` — but a **lower version** and a **tiny executable** inside. It never has to run. Its only
> job is to register the family on the console, cheaply, so that the real package arrives as an update.

1. Make a folder with any small `.exe` renamed to `BloodyRoar2_Recompiled_USA.exe` (a couple of MB is
   plenty — it is never launched), and give it the `mods\bundled` folder the packer expects, even empty:

   ```powershell
   New-Item -ItemType Directory -Force <seed-build>\mods\bundled | Out-Null
   Copy-Item C:\Windows\System32\notepad.exe <seed-build>\BloodyRoar2_Recompiled_USA.exe
   ```

2. Package it with a **lower version** than the real one, everything else the same:

   ```powershell
   powershell -ExecutionPolicy Bypass -File tools\empaquetar-uwp.ps1 `
        -Build <seed-build> -Salida <out> -Certificado <thumbprint> -Version 0.0.0.1
   ```

3. Install that one first (8.2), with the VCLibs dependency.
4. Then install the real one with its own, higher version, and the portal takes it as an update. It goes
   in.

### Removing it from the console

⚠ **Your saves go with it.** They live inside the package, in its `LocalState`, and disappear with it. To
keep them, download them first from the Device Portal's **File explorer**: they are under
`LocalState\PSXRecomp\SCUS-94424\saves`.

To uninstall, in the Device Portal: **My games & apps**, find the game in the list, and **Remove**.
Nothing on your PC is touched.

If what you want is to **update** without losing them, do not uninstall: install a package with a
**higher version** on top.

## 9. The disc

It lives in the app's own data folder, which that first launch created:

```text
…\Packages\<identity>\LocalState\PSXRecomp\SCUS-94424\
    disc\    bios\    saves\    logs\
```

Upload through the Device Portal's **File explorer** → **LocalAppData** → your package → `LocalState` →
`PSXRecomp` → `SCUS-94424` → `disc`:

- the `.cue`, as it is;
- the `.bin`, **split into parts**. The portal answers 500 to a 527 MiB upload because it stages it
  through `D:\DevelopmentFiles`. `tools\partir_disco.py` cuts it into 150 MiB pieces — four of them for
  this game — named `<disc>.bin.parte1`, `.parte2`, …:

  ```powershell
  python tools\partir_disco.py "<your disc>.bin" <output folder> 150
  ```

  The entry point concatenates them on the next boot, once, and leaves the parts where they are. The log
  says `partes: 4 unidas, 552729408 bytes` when it worked. You can delete the parts from the console
  afterwards.

**No BIOS upload is needed**: the free OpenBIOS travels inside the package. If you would rather use your
own retail BIOS, put it in `bios\` and the runtime will pick it up.

On every boot the entry point also seeds `game_us.toml`, `game_options.toml` and the mods from inside the
package (so a new package really does update them), leaves `settings.toml`, `input.ini` and
`keybinds.ini` alone if they already exist (they are yours), writes `bios.cfg` and `disc.cfg` with
**absolute** paths, and redirects the runtime's output to `logs\salida.txt` and `logs\errores.txt`.

Read those two logs. On a console they are the only thing you have.

⚠ **The logs are locked while the game is running.** To read them, stop the app first.

## If something goes wrong

| Symptom | Cause |
|---|---|
| `Failed to launch the application` | Several things cause this and each hides the next; [`HOW-IT-WORKS.md`](HOW-IT-WORKS.md) §1 lists them. The two most common: the **VCLibs dependency** missing or the wrong file, and having built with `vcvars64` instead of `vcvarsall x64 uwp` |
| The package installs but there is no window | Check `logs\errores.txt`. If it says `Could not initialize OpenGL / GLES library`, the software renderer was not forced before the window was created — step 4 did not finish |
| It installed fine and now the app is gone from the list | You installed the **same version** twice. That unregisters the package. Repackage with a higher `-Version` |
| `cannot launch with selected mods: package does not target this game/image: br2.enhancement.widescreen` | The mods are validated before the disc is resolved. The packer strips `disc` from the bundled `game_us.toml` and `parche_uwp_disco_mods.py` resolves it earlier; if you repackaged by hand, that key is probably back. The quick test is `-SinPanoramico`: if it boots without the mod, this is it |
| No controller | Both slots must be on "auto" (`parche_uwp_mando.py`, and `config\settings.toml`). The log says `opened controller for slot:` when it works |
| Nothing is ever saved | `memcard_dir` is relative and resolves against the read-only install folder. `parche_uwp_escritura.py` re-anchors it; the log confirms the writable state directory |
| The widescreen does not kick in | It is on, but the runtime only applies it **when the game proper starts**: the attract demo stays 4:3 even with `mod selected fixed display aspect 16:9` in the log. Check it by playing, not by taking a screenshot of the boot |
| The game restarts after you go Home | Expected: Developer Mode terminates a game that goes to the background, and wiring the save-state machinery to the activation state is not done in this port. It is an open issue |
| Fights below 60 FPS | Known and not solved — see the README. The software rasteriser runs out of time in the heaviest scenes |
